I finished Ph5 structs 3/5 (save data) for session 31. Everything comes from reading the code, not from running it; the emulator checks are still queued.

**What the boot code does**
- **`BootSaveCheck` `31:F0A4`** (was `BootSub`) runs on every boot and checks three save images:
  - **Slots 0 and 1:** each slot has a primary and a backup copy. If the two copies match, only the "AMI" tag is checked. If they differ, each copy's checksum is compared with the stored one (`$70F0-$70F3`), and a good copy overwrites the bad one. If neither passes, the slot is reset from a built-in default page at `23:BE00` (the new-game starting values).
  - **Current image `$7D00`:** it must equal its mirror at `$6D00` and carry the AMI tag. There is no checksum.
- **`ColdSaveInit` `31:F1CD`** (was `ColdInitSub`) always resets the current image on power-on. The two save slots survive.

**Bugs in the original code that the web port has to reproduce or knowingly change**
1. **NPC state is not saved.** The save copy was meant to cover 512 bytes (story flags plus NPC state). The copy routine's length bug cuts it to 257, so only `npc_state[0]` is kept, and every other NPC's state comes back as 0 after loading.
2. **Checksum seed.** The boot checksum routine `31:F23D` adds onto whatever `$16` already holds instead of starting from 0. So the repair path only works by luck. It only runs when a save was interrupted between writing the primary and the backup.
3. **Slot 1 asymmetry.** When slot 1's primary passes, the code still falls into the backup check. If that fails, slot 1 is wiped. Slot 0 skips that check.
4. **Boot copy is one page off.** `31:F3A2` copies the save image into the flag and NPC-state areas one page too early. Loading the game (`LoadGameAndInit`) overwrites both pages, so it looks harmless. I haven't proven that loading is the only way into gameplay, so that is queued.
