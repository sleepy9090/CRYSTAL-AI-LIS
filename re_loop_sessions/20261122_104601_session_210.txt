I used session 210 on the last open part of the low-priority leftovers task, (c): CPU overruns. I didn't add a lag model to the port. Instead I measured where the overruns come from, and that showed the cheap approach won't work. The task stays unchecked, with what's left written into its (c) text. No port code changed, so I didn't re-run the checks.

**How a lag frame happens.** Each main-loop pass ends at `30:C919`, where it clears the "frame ready" flag that the NMI (vertical-blank interrupt) sets. If a pass is still running when the NMI comes, the NMI sees the flag still set and skips the sprite upload. The clear at `C919` then makes the loop wait a whole extra frame.

**What tools.emu shows.** I measured two areas: $81 (461 passes, 18 lag) and $59 (468 passes, 11 lag).
- **Threshold:** a pass that starts at line 252 lags if it needs more than about 28,500 CPU cycles. The largest pass that didn't lag was 28,431 cycles; the smallest that did was 28,966.
- **Cost per stage:**
  - **ObjUpdateAll:** 6,300–13,800 cycles.
  - **ObjSpriteDraw:** 4,900–11,600.
  - **ObjCollideAll:** about 1,200–2,200 on even frames and 2,700–4,000 on odd frames, plus the hit handlers.
  - **CameraTick:** about 1,250, but 3,700 or 5,200–5,760 when it draws a new row during vertical scrolling.
- **Causes:** 22 of the 25 real overruns are a CameraTick row draw on a pass where the object updates and sprite drawing are already heavy. Two had no row draw, just heavy updates and sprites. One is a sword kill in ObjCollideAll.
- **Not overruns:** four of the lag frames have an ObjCollideAll spike of 8,400–11,000 cycles. These are the player-hit pause frames, which the port already reproduces.

**Why the cheap model fails.** I fitted the cycle counts against how many RAM reads and writes the port makes per frame. Over area $81's 99 passes before the first lag, the estimate is off by 672 cycles on average and up to 2,496. The gap between lagging and not lagging is only about 500 cycles, so this can't tell which frames lag.
