I've traced the bank 28 `$800E` object sprite pass and marked that task done in `REVERSE.md` (new section "Object sprite pass"). All of this comes from reading the disassembly; nothing has been checked in an emulator yet.

- **Object table:** there are 32 object slots. Each slot's fields live in parallel arrays: position at `$70/$90` (X low/high) and `$B0/$D0` (Y low/high), plus an active flag, sprite id, tile offset, flags, animation counter, an overlay sprite id, and the computed screen X/Y. The flags byte at `$0380` has 7 bits worked out, including "draw behind background", "flicker every other frame" and "offscreen".
- **Draw order:** each frame, `$07FF` is decremented and its low two bits pick one of 4 fixed 32-slot orderings at `28:83DC`. It is not a simple rotating start slot, as the old label said. OAM sprite 0 is never used here, and unused OAM entries are hidden at the end.
- **Sprite data format:** each sprite record is: sprite count, frame mask, then per-frame lists of 4-byte entries (x offset, y offset, attributes, tile). The current frame is the animation counter divided by 8, masked. Pointer tables are at `28:845C` (ids `$00-$7F`) and `28:855C` (ids `$80-$FF`). A record starting `FF lo hi` draws another record mirrored left-right, which is how facing variants are stored. An x offset of `$80` ends a frame early. Attribute bit 2 marks lower-body parts that get hidden when the object is sinking (flag bit 6).
- **Object 1 is the player:**
  - its sprites flash to palette 0 when `$0710` bit 7 is set (likely damage);
  - an 8-sprite ring is drawn around it: either an orbit driven by `$06C0` and a sine table at `28:81BA`, or a burst countdown on `$06C1`.

I also found one piece of dead code: a value derived from `$0340` bit 7 is computed but never read.
