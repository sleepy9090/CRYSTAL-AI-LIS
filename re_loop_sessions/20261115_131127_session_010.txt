Session 10 is done. The task was to find compressed data and its decompressors. **There is no compression in the ROM.** Everything was checked statically; none of it has been run in an emulator.

**How the level graphics are stored**
- **Screens:** each byte in the `$6300` screen grid points straight at its screen. `31:EF36` uses the top 2 bits to pick which pair of ROM banks to map (banks 0–7) and the low 6 bits to pick a 256-byte page in it.
- **Screen pages:** each page is a plain 16×15 grid of metatile ids (the 16×16-pixel blocks levels are built from). The last 16 bytes of each page hold other tables: palette records in banks 2/3 and spawn records in banks 4/5. That explains the "page tail" layout seen in sessions 8–9.
- **Metatiles:** each metatile is drawn from four 256-byte pages in banks 8/9, one per 8×8 corner, chosen by the area's tileset value `$67`.
- **Visited screens:** if a screen has been visited, metatile ids below `$20` are swapped through a lookup table in bank 9 at `$BE00`. My guess is this shows opened doors or broken blocks; I haven't confirmed it.
- **Title/menu screens:** banks 17 and 18 share a small drawing library. It fills a whole screen with one tile, or copies a plain "width, height, then tiles" rectangle, either at once or one row per frame.

**Why I'm confident nothing is compressed**
- I checked all 49 places that write to the PPU's video memory. The ones in the fixed banks copy from RAM buffers, and the only ones reading ROM data are the plain rectangle copiers above.
- I searched for the byte patterns compression code usually uses (a data read followed by a high-bit test). All 10 hits turned out to be something else: sprite offsets, an object script, or data that only looks like code.
- I wrote `tools/bank_entropy.py`, which measures how random each bank's bytes are. No 1KB block reaches 7.0 bits/byte; compressed data would be 7.5 or more.

So `tools/decompress.py` isn't needed, and the web port can read screens, metatiles and tile maps straight from ROM offsets.
