Session 23 finished task **Ph4 assets 1/5 (tiles + palettes)**. Both new tools ran without errors, and I checked the two output images by eye.

**New tools and outputs**
- **`tools/extract_tiles.py`** dumps all 128 CHR 1KB banks to `gfx/chr/chr_000-127.png` (16×4 tiles, grayscale, 4× scale) plus one combined sheet, `gfx/chr_all.png`. It takes about 3 seconds. No bank is blank. Banks 0–63 are background art (including the font, HUD and end-screen letters) and banks 64–127 are sprite art.
- **`tools/palette_dump.py`** renders every palette record from banks 2/3 to `gfx/palettes.png` and `gfx/palettes.json`. It uses the common NES colour table (the one starting `7C7C7C 0000FC`, from the NESdev wiki "PPU palettes" page); the tool notes that it is an approximation. The JSON also lists which areas use each record as a background or sprite palette. This also covers the palette tool asked for in the older "area follow-ups 3" task.

**Findings**
- **Correction:** there are **256** palette slots, not 512 as REVERSE.md said. Sprite palette ids are offset by +`$B0` with 8-bit wrap-around, so sprite ids `$50`–`$FF` reuse background slots `$00`–`$4F`.
- **Palette data:**
  - All 256 slots hold valid colour values (none above `$3F`).
  - 144 bytes are `$FF`, meaning "use the background colour", and 17 slots are entirely `$FF`.
  - Areas use 178 slots: 131 as background palettes and 48 as sprite palettes.
- **Upload to the PPU:** the only routine that writes palette memory (`$3F00`) is the new `PaletteUpload` at `31:F8CB`, called once per frame from the NMI at `31:F40F`.
  - It does nothing while bit 7 of `$51` is set.
  - It copies the background colour into the first entry of every 4-colour group, so the bytes at `$6144/48/…/5C` in the buffer are never sent to the PPU.
  - It finishes by resetting PPUADDR to `$3F00` and then `$0000`.
