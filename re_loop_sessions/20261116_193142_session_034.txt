**New package `tools/emu/`** (pure Python, nothing third-party):
- **`loader.py`** reads the ROM using the existing `nesrom.py` and checks the header: MMC3, 32 × 8KB PRG banks, battery save.
- **`memory.py`** is the CPU's address map:
  - RAM, mirrored the way the console does it.
  - Hooks for the parts that don't exist yet (graphics, sound and controller registers). The sprite-copy register (`$4014`) already makes the CPU pay its 513-514 cycle delay.
  - Battery save RAM at `$6000-$7FFF`, and per-address read/write watches for later debugging.
  - Until the bank-switching chip (MMC3) is written in emu 2/6, a fixed stand-in maps banks 0/1/30/31 and records the game's writes to it.
- **`cpu.py`** is the processor. Its opcode table comes from `instruction_set.py`, so it runs all 151 official opcodes plus the few unofficial ones listed there. Cycle counts are exact, including the extra cycles for crossing a page and for taken branches. It also handles the known 6502 address-wrap bugs, BRK, NMI and IRQ. Decimal mode is ignored, as on the real NES chip.
- **`test_cpu.py`** has 23 hand-written tests covering flags, arithmetic overflow, address wrapping, cycle counts, the stack and interrupts. It also has one test against the real ROM: starting from the reset vector `31:F2A4`, the CPU reaches `SwitchBank16` (`$C40E`) after 261 instructions, asking for bank pair `$0C` (banks 24/25). That matches what REVERSE.md already says the reset code does.

**Not modelled:** dummy reads and writes, the one-instruction delay before an IRQ after CLI/SEI/PLP, and an NMI taking over a BRK. These are written down in REVERSE.md, to be added only if a trace comparison ever needs them.
