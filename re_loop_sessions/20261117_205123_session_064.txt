I traced the rest of the NMI (`31:F3B6`-`F421`) and marked the task done. This was all done by reading the disassembly; I didn't check any of it in the emulator. The top-level NMI was already documented, so this session filled in what was missing.

**What I found**
- **PPU update queue (`30:C67D`):** each queue entry is 4 bytes: address high, address low, length, and the source offset in `$6000`.
  - Bit 6 of the address high byte makes the PPU write down a column instead of across a row.
  - Bit 7 of the high byte tells it to send the next entry in the same NMI. Without that bit, only one entry goes out per NMI.
  - If the length byte has bit 7 set, it copies 64 attribute bytes from `$6100` instead (`30:C6E7`).
  - After an entry is sent, its source byte is set to `$FF`.
- **Bit 7 of `irq_mode` (`$51`)** only stops the palette upload; the NMI mode still runs. Mode 8 has no entry in the table, so `irq_mode`=8 would crash, but nothing ever sets it.
- **All 10 NMI modes** now have a table in REVERSE.md. For each mode it lists where the scroll and CHR banks come from, which IRQ split it sets up and at which line, whether the sound driver runs from the NMI, and every place that sets the mode. To find the setters I wrote a small new tool, `tools/zp_writers.py`.
- **Mode 4 is dead code.** It was a shop-door graphics effect (`31:FE01` opens, `31:FE18` closes). The shop entry and exit routines call the `RTS` bytes just before each one (`31:FE00` and `31:FE17`), so the effect never runs. Mode 4 also writes to `$F451`, which the cartridge mapper treats as "IRQ on". That's harmless, because the next instruction turns the IRQ on anyway.
- IRQ handlers 3 and 5 aren't set up by any NMI mode, so they can only be reached from another IRQ handler. I left the IRQ handler bodies for the next task in the list.
